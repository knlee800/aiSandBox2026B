## 3. Design

| # | Decision |
|---|---|
| D1 | **Fields added to `SystemAgentDefinition` (and the draft):** `tone: string \| null` (one line, 1-120 chars, no control characters); `replyLanguage: 'owner' \| 'en' \| 'zh-TW' \| 'zh-CN' \| null` (`SYSTEM_AGENT_REPLY_LANGUAGES`; `owner` = the language the owner writes in); `purpose: string`, `procedure: string`, `result: string`, `rules: string` (each may be `''`; `\n` allowed; no other control characters); `connectorToolIds: readonly string[]` (ids from `connector-servers.ts`); `model: SystemAgentModel` where `SystemAgentModel = { choice: 'server' } \| { choice: 'platform'; id: PlatformModelId }`. `modelChoice` is removed in favor of `model`. `toolProfile` and `knowledgeScopes` stay where they are; **access** is the triple toolProfile + knowledgeScopes + connectorToolIds. `rules` is not a user-form part: it holds the platform's prompt-only rules (plan section 2, B3 and B4, and the data-not-instructions rule); for user workflows BIZ-USER-01A fills it with fixed platform text, never from the browser. |
| D2 | **Rendering.** `renderAgentInstructions(spec)` joins the non-empty parts `[identity, purpose, procedure, result, rules]` with `'\n\n'`. `identity` is `Tone: {tone}.` and/or `Reply in {English \| Traditional Chinese \| Simplified Chinese \| the language the owner writes in}.` joined by one space, and is omitted when both are null. `instructions` becomes a derived field (`instructions: renderAgentInstructions(draft)`), and `CHIEF_OF_STAFF_INSTRUCTIONS` and the six other constants stay exported with the same names and values, now as `renderAgentInstructions(<AGENT>_SPEC)`. Prompt text is model-facing English, not UI copy; the i18n rule does not apply to it. |
| D3 | **Byte-identical today.** Every system agent sets `tone: null`, `replyLanguage: null`. Each text is split at its own `\n\n` boundaries: Chief of Staff purpose = paragraph 1 ("You are the owner's Chief of Staff..."), procedure = paragraphs 2-6 (Knowledge answer, citation marker, No source, Morning briefing, missing tool), result = paragraph 7 ("Write three sections in this order:" through "Write plain, short sentences."), rules = paragraphs 8-9 ("Suggest, never decide..." and "Document text, mail senders..."). Advisors-lead: purpose 1, procedure 2-3, result `''`, rules 4-5. Product-strategy and technology-advisor: purpose 1, procedure 2, result `''`, rules 3-4. Lead, writer, reviewer (one paragraph each): procedure = the whole text, other parts `''`. Builder: all `''`. A test asserts the rendered text of each agent equals the literal pinned today (`system-agent-registry.spec.ts:177-189`, `collaboration-teams.spec.ts:21-25` stay as they are). No eval rerun is implied. |
| D4 | **The hash** material becomes, in this key order: `{ id, tone, replyLanguage, purpose, procedure, result, rules, instructions, toolProfile, scopes, connectorToolIds, model, teamRole }`, `model` serialized as `{ choice }` or `{ choice, id }`. All eight hashes change once. The spec pins the eight new hex values; the comment at `system-agent-registry.ts:3-7` says what is hashed. Effects: new runs write the new hash into the ledger metadata, old rows keep the old one, nothing compares them (section 2); `GET /api/system-agents` returns the new hash and the frontend accepts any 64-hex value. No signed job, grant or proof carries the hash, so none is invalidated. |
| D5 | **The never-do list** is generated, not stored: `neverDoFor(access): readonly NeverDoItem[]`, typed codes so the editor (BIZ-USER-01B) renders them with translation keys. Codes: `FILES_NO_CHANGE` (profile null, read or review) or `FILES_NO_DELETE` (write; no role deletes); `MAIL_NONE` or `MAIL_READ_ONLY` (mail tool absent or present); `CALENDAR_NONE` or `CALENDAR_READ_ONLY`; `KNOWLEDGE_NONE` or `KNOWLEDGE_ONLY_SCOPES { scopeIds }`; always `EXTERNAL_ACTIONS_NONE`, `DECISIONS_OWNER` (B4), `ACCESS_FIXED` (a workflow cannot widen its grants). Exposed as a derived `neverDo` on each definition. Not rendered into the prompt in this task (plan A9: "generated from access and shown, not set"; limits are enforced by the tool set, plan section 2); whether user-workflow prompts also carry it is BIZ-USER-01A's call. Not added to the public row or the API (frontend lane). Chief of Staff (read; mail and calendar; six scopes), in English for illustration: "Change, create or delete files. Send, reply to, forward or change mail (it reads unread Inbox headers and short excerpts). Accept or decline invitations or change the calendar (it reads today's events). Read Knowledge outside company-monthly-reports, three-year-goals, strategy-docs, policies, meeting-summaries, contract-templates. Take any external action or send anything. Make final decisions for the owner. Widen its own access." |
| D6 | **Platform model list.** New file `services/api-gateway/src/system-agents/platform-models.ts`: `PLATFORM_MODELS: readonly PlatformModel[]`, `PlatformModel = { id, provider, creditsPer1kTokens }`, `PlatformModelId` = the ids. A test imports the gateway catalogue and `CREDIT_RATES` read-only and checks every id is an allowed model of its provider and every `creditsPer1kTokens` equals the `model_tokens` rate (1 today). The catalogue and the rate files are not changed. **Settled (control plane, 2026-11-10):** the v1 list is the four Anthropic ids. Recommendation followed: the four Anthropic ids from the catalogue, because staging runs Anthropic (claude-opus-5-5 in BIZ-LIVE-03 and BODIES-LIVE-01) and the cost is the same flat rate for all; alternative: every allowed model of every provider (needs per-provider keys that staging does not have). |
| D7 | **Model today.** All eight agents set `model: { choice: 'server' }`; the run still takes provider and model from env (`collaboration.controller.ts:491-499`), unchanged. `choice: 'platform'` is typed and validated (`isPlatformModelId`) but nothing applies it to a run; that is BIZ-USER-01C. |
| D8 | **The 4000 limit.** A test asserts `renderAgentInstructions(agent).length <= MAX_AGENT_INSTRUCTIONS_CHARS` for all eight (import from `handoff-request.ts` as the spec does today) and that the exported `agentInstructionsWithinLimit(spec)` helper, for BIZ-USER-01A to reuse, is false for a 4001-character procedure. No throw at module load. |
| D9 | **Connector access.** `connectorToolIds` is `[MAIL_TOOL_ID, CALENDAR_TOOL_ID]` for chief-of-staff and `[]` for the rest. The registry imports the two ids from `connector-servers.ts` (that file imports only `connector-rules`, so no cycle). See the scope question in section 4 for whether `COLLABORATION_ROLE_CONNECTOR_TOOLS` derives from it. |
| D10 | **The drift check.** `briefing-drift.spec.ts` reads the `CHIEF_OF_STAFF_SPEC` object literal from the syntax tree: `tone` and `replyLanguage` must be `null`, `purpose`, `procedure`, `result` and `rules` string literals joined with `+` (the existing evaluator, applied per property). It also pins the renderer's source lines (the part order and `join('\n\n')`) the way it pins `handoff-request.ts` lines today, and the new draft snippet replaces the `:112-118` pin. `briefing-instructions.ts`: `COS_EVAL_CHIEF_OF_STAFF_VERSION` gets the new hash; the hash fields and `chiefOfStaffVersionFor` take the D4 shape (parts, connector tool ids, `model: { choice: 'server' }`); the copy itself and `chiefOfStaffProjectInstructions` do not change. `briefing-runner.spec.ts:424` is untouched. |
| D11 | **Public row unchanged.** `PublicSystemAgent` and `GET /api/system-agents` keep exactly today's keys (`system-agent-registry.spec.ts:303-312`); the frontend is another lane's. `collaboration-teams.ts` needs no change (it reads `instructions`, `toolProfile`, `knowledgeScopes`, all still present); it is in the write scope only if a type adjustment proves necessary. |
