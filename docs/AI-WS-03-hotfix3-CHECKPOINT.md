## Implementation Summary

### `deleteWorkspaceFile` — change on failed responses only

Before: any non-OK response threw immediately with a generic message:
```
throw new Error(`File delete failed (${response.status})`);
```

After: when the response is not OK, the helper first attempts to read the JSON body:
1. `response.json()` is awaited inside a `try/catch`.
2. If the parsed body has a non-empty string `message`, it is trimmed and thrown as the error message.
3. If JSON parsing fails (non-JSON body, network issue, etc.), `backendMessage` stays `null`.
4. If no useful backend message was found, the existing fallback `File delete failed (<status>)` is thrown unchanged.

Successful delete responses (`response.ok === true`) are unaffected — no body read, no change in behavior.

**Effect:** A backend 404 response of `{ "message": "File not found: index2.html" }` now surfaces exactly as `File not found: index2.html` in the file-action result, rather than the generic `File delete failed (404)`.

## Tests Added

Two new focused test cases in `workspace-file-navigation.logic.test.ts`:

1. **Surfaces backend delete error messages when available** — response `ok: false`, `status: 404`, JSON body `{ message: "File not found: index2.html" }` → throws error matching `File not found: index2.html`.
2. **Falls back to generic delete error when backend body is not JSON** — response `ok: false`, `status: 404`, `json()` throws `SyntaxError` → throws error matching `File delete failed (404)`.

All 7 pre-existing tests pass unchanged (9 total).
