## Implementation Summary

### `workspace-ai-file-actions.logic.ts`

- Added `RISKY_BATCH_ACTION_COUNT_THRESHOLD = 3` and `RISKY_CONTENT_SIZE_THRESHOLD = 20_000`.
- Added private `isRiskyFileActionPath(path)` — returns `true` for:
  - `.env`, `.env.*`, `*.env`, `*.env.*`
  - `package.json`, `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`
  - `docker-compose.yml`, `docker-compose.yaml`
  - `*.config.js`, `*.config.ts`, `*.config.mjs`, `*.config.cjs`
- Added exported `isRiskyFileActionBatch(actions)` — returns `true` when:
  - `actions.length > 3`
  - any action content length exceeds 20,000 chars
  - any action path matches `isRiskyFileActionPath`
- Extended `WorkspaceExecutionFileActionApplyStatus` to include `'awaiting-confirmation'`.
- Added `confirmationRequired: boolean` to `WorkspaceExecutionFileActionState`.
- Extended `isWorkspaceExecutionFileActionState` to accept `'awaiting-confirmation'` status and treat `confirmationRequired` as optional in persisted data (normalised downstream).
- `applySequentialFileActions` is unchanged.

### `frontend/app/[locale]/app/page.tsx`

- Added `pendingConfirmationExecutionIdsRef` (Set): tracks executions currently waiting for user confirmation.
- Added `cancelledFileActionsExecutionIdsRef` (Set): tracks executions the user cancelled; prevents re-opening confirmation on duplicate delivery.
- Extracted `applyExecutionFileActions(executionId, source, executionSessionId, token, actions)` — acquires idempotency guard then calls `applySequentialFileActions`, sets final state; only called for safe or confirmed executions.
- Restructured `maybeApplyExecutionFileActions`:
  - early-return if execution is in the cancelled set
  - early-return if execution is already in pending-confirmation set (re-render stability)
  - if `isRiskyFileActionBatch(actions)`: adds to pending-confirmation set, sets state to `awaiting-confirmation`, returns without applying
  - otherwise: delegates to `applyExecutionFileActions` (safe path, same as before)
- Added `handleConfirmExecutionFileActions(executionId)`: removes from pending set, delegates to `applyExecutionFileActions`.
- Added `handleCancelExecutionFileActions(executionId)`: removes from pending set, adds to cancelled set, sets state to `skipped / user-cancelled`.
- Updated `consumeExecutionFileActions`: checks applied/cancelled/pending-confirmation sets before resetting state to `pending` — prevents duplicate deliveries from regressing already-resolved executions.
- Added `confirmationRequired: false` to all existing `applyStatus: 'pending'` and `applyStatus: 'skipped'` state construction sites for type correctness.
- Wired `onConfirmExecutionFileActions` and `onCancelExecutionFileActions` into `WorkspaceShell` props.

### `workspace-shell.tsx`

- Added optional `onConfirmExecutionFileActions?: (executionId: string) => void | Promise<void>` and `onCancelExecutionFileActions?: (executionId: string) => void` props to `WorkspaceShell`.
- Forwarded both to `WorkspaceChatPanel`, which forwards them to `WorkspaceAssistantFileActionSummary`.
- In `WorkspaceAssistantFileActionSummary`:
  - extended `hasRenderableResults` to include `applyStatus === 'awaiting-confirmation'` batches
  - added inline `div` rendered only when `applyStatus === 'awaiting-confirmation'`:
    - amber border notice explaining approval is required
    - bullet list of file paths (`data-testid="workspace-chat-file-actions-awaiting-list"`)
    - `Apply` button (`data-testid="workspace-chat-file-actions-confirm-button"`) calls `onConfirm`
    - `Cancel` button (`data-testid="workspace-chat-file-actions-cancel-button"`) calls `onCancel`
  - UI is minimal and inline; no modal, no diff viewer

### `workspace-chat-thread.logic.ts`

- When deserialising persisted `fileActionState`, the `confirmationRequired` field is normalised: `candidate.fileActionState.confirmationRequired === true` (explicit boolean coercion). Legacy messages without the field parse to `false` and are kept rather than dropped.

## Honest Notes

- The existing idempotency guard (`appliedFileActionsExecutionIdsRef`) is now only acquired when an execution is actually being applied (safe path or confirmed). Risky batches use a separate `pendingConfirmationExecutionIdsRef` so they are not accidentally marked applied before the user responds.
- Cancelled executions use a separate `cancelledFileActionsExecutionIdsRef` so later duplicate stream/status deliveries do not reopen the confirmation path.
- Legacy persisted `fileActionState` objects without `confirmationRequired` are normalised to `false` during chat-thread parsing so existing history is not lost.
- The coherence and autosave follow-up path (`maybeRunExecutionCoherence`) remains gated on `applyStatus === 'applied'` — it does not fire for awaiting-confirmation or cancelled states.
