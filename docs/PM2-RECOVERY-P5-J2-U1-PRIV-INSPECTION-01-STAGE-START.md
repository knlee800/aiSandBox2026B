### 17.3 Timeouts, metadata, local limits, and failure handling

Every remote inspection command above uses `timeout --signal=TERM --kill-after=1s 14`. The proposal does not use an 8-second wrapper. An 8-second wrapper would be a tightening only for a command that actually carries it. This proposal does not rely on that exception. Do not record `perCommandTimeoutSec=15` as the wrapper duration. Do not record `perCommandTimeoutSecTightened`. Record `termSec=14`, `killAfterSec=1`, and `escalationSec=15`. `deadlineSec=120` names the supervisor deadline only.

Chosen policy, requiring adoption with this proposal: cancellation escalation stays inside the existing 15 s budget. It is not `timeout 15` plus another second.

| Point | Time from wrapper start | What it is |
|---|---|---|
| Timeout threshold | 14 s | `timeout` sends SIGTERM to the inspection process it spawned |
| Cancellation grace | 1 s | Wait after TERM before escalation |
| Escalation time | 15 s | `timeout` attempts SIGKILL on that same process |
| Confirmed direct-child exit | The wrapper process has exited | Status 0, the command's own status, 124, or 137, as below |
| Unconfirmed termination | The wrapper has not exited, or only the local `ssh.exe` exit is known | Do not treat the attempt as success |

The 120 s deadline, the capture cap of 65536 bytes and 2000 lines, the 10 s connect timeout, and keepalive 15 s × 4 stay at the frozen numbers. The 15 s figure is the escalation time. It is not a claim that the command is dead at 15 s.

Frozen §5 item 5 forbids kill, pkill, and other signals. This proposal adds one exception, and only if the proposal is later adopted:

- TERM at 14 s and the KILL attempt at 15 s may reach children that belong to the wrapped inspection command, such as `stat` under that `sudo`. They are not aimed at a named host PID.
- The exception does not authorize a signal to PID 1193674, PID 844871, a PM2 daemon, an application process, or any process found by a scan.
- Exit 124, the TERM path in INVENTORY-01 §2.0, means `timeout` sent TERM and reported that path. It does not prove every descendant has exited.
- Exit 137, the KILL path in that same section (128+9), means escalation was reported. It does not prove every descendant has exited. Classify 137 as TIMEOUT, not SUCCESS, not absence, and not PID-GONE. Discard stdout.
- If the wrapped process is still running after the KILL attempt, or the wrapper status is not observed, termination is unconfirmed. Keep the script `STOPPED` if the script can see the failure. Do not send another signal.

Script-visible stops are enforced by the remote script exiting before the next command. The local supervisor does not perform that exit.

Local cap and deadline use a different mechanism, read from INVENTORY-01 and from this task's retained supervisor record. This window did not execute it.

- Session state for the cap and the deadline lives in the local supervisor: `bytesReserved`, `linesReserved`, `limitExhausted`, and the `Stopwatch` elapsed since `process.Start()`, before stdin delivery (INVENTORY-01 §4.3.1–§4.3.3). It does not live in remote bash.
- The stdin writer writes the whole script, flushes, and closes stdin (INVENTORY-01 §4.3.1 step 4). This task's `record.json` records `StdinDelivered=true` for the 2026-09-30 run. Later commands are already in the script bash has accepted. The writer does not wait for a command result before sending the next line.
- On `limitExhausted` or elapsed past the deadline, the poll loop sets `pollTrigger` and T1 calls `process.Kill()` on the local child. For this carrier that child is `ssh.exe` (INVENTORY-01 §13.4: the production child has no Windows descendants; `Process.Kill()` is not a remote process sweep). T2 waits up to 5 s. T3 sets `killUnconfirmed` when `HasExited` stays false. `HasExited` and `ExitCode` confirm only that local process.
- INVENTORY-01 §4.3.6 and §0.11 / §9.9: after the local SSH client dies, the TCP connection drops and remote `sshd` should send SIGHUP. Remote cleanup is not guaranteed. A local `STOPPED` label and closing SSH do not by themselves stop bash from continuing lines it has already read.
- The in-flight remote command keeps running until its own wrapper, a SIGHUP that actually arrives, or something else stops it. None of those is established by the local `Kill` record. Output already retained is partial and is not a complete result.
- Evidence that can confirm termination is only `HasExited` for local `ssh.exe`, plus an observed wrapper status if that status was actually read. `killUnconfirmed`, a missing wrapper status, or a channel drop leaves remote bash, `timeout`, `sudo`, and the utility unconfirmed. This proposal does not add a later observation to resolve that.

**Execution readiness: BLOCKED** for any later session that relies on the capture cap or the 120 s deadline to prevent subsequent remote commands.

Missing mechanism: a stdin writer that sends the next inspection command only after the local supervisor has the previous command's wrapper status and has not set `limitExhausted` and has not passed 120 s. The current writer does not do that.

Minimum separately authorized work: that writer change in the supervisor, with the record showing whether further stdin was withheld, distinct from `Kill` of `ssh.exe`. This window does not implement that change and does not claim the existing carrier already has it. No new authorization is created here.

A classifiable path DENIAL does not by itself stop the script. `sudo` refusal does. When an error cannot be placed in exactly one outcome class, it is UNCLASSIFIABLE, stdout is discarded, and the script stops.
