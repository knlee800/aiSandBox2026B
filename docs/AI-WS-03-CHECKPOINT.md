## Implementation Summary

### Bounded Delete Slice

AI-WS-03 is a bounded delete slice.

- The AI file-action contract now supports `delete` alongside `create` / `write` / `update`.

### ai-service

- `types.ts` now models file actions as a discriminated union:
  - `create` / `write` / `update` require `content: string`
  - `delete` requires `path: string` only
- `file-actions.parser.ts`:
  - accepts `delete`
  - parses delete actions with `path` only
  - keeps existing path normalization and traversal protection logic
  - still requires `content` for non-delete actions
- `worker.processor.ts` updates the prompt contract so the model is explicitly told:
  - `delete` exists
  - delete actions must omit `content`
  - no create/change/delete claim is valid without matching `file-actions`

### api-gateway

- Added user-facing `DELETE /api/sessions/:id/files/delete`.
- The route uses the same ownership and terminated-session guard pattern as the existing file read/write routes.
- Added `deleteSessionFile(sessionId, path)` to `ContainerManagerHttpClient`.
- The client proxies to the existing container-manager file delete endpoint.

### frontend

- Added `deleteWorkspaceFile(...)`.
- Extended AI file-action typing/guards to accept delete without content.
- Any batch containing delete always classifies as risky.
- Delete therefore always flows through the AI-WS-02 confirmation path before applying.

### `frontend/app/[locale]/app/page.tsx`

In the confirmed apply path:

- `create` / `write` / `update` still use the existing write path
- `delete` calls the delete helper, then refreshes the file tree
- if the deleted file exactly matches the selected/open file, editor state clears safely by resetting:
  - `selectedFilePath`
  - `selectedFileContent`
  - `savedFileContent`
  - `fileSaveState`
  - `fileSaveError`
- if delete leaves the workspace with no files, the file surface moves to the existing empty state
